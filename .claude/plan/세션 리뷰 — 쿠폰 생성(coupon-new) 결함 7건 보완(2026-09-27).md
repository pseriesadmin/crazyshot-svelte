## 1. 4+7 — 쿠폰 코드 채번 "발행 순번"(issue_seq) 신설

### 배경
상품(products)의 "부모 순번(2단 계층)" 패턴이 쿠폰 코드조합 화면(`buildComboPreview`)에는 이식돼 있었지만, 실제 서버로 전송되는 `codeSeriesPayload`에 `parent_max_sequence` 필드 자체가 빠져 있었고, 채번 RPC(`cms_create_coupon`)도 이 값을 전혀 읽지 않아 관리자가 설정한 "발행 순번 상한"이 아무 효과가 없었다. 또한 발행관리 목록의 "코드" 컬럼이 같은 분류로 여러 쿠폰을 만들어도 전부 동일한 0-패딩 미리보기 문자열만 보여줘 레코드 구분이 안 됐다.

### 설계 핵심
- **`coupon_parent_sequences`(Migration #555)**: `product_parent_sequences`(Migration #214)와 완전히 동일한 원자 카운터 패턴이나 별도 테이블(카운터 공유 없음). key = `category_code + year_month`.
- **`cms_create_coupon`(Migration #556)**: `p_code_mode='sequenced'`일 때 이 카운터로 `issue_seq`를 원자 채번 → `code_series`에 `jsonb_build_object('issue_seq', v_issue_seq)`로 병합 저장. `parent_max_sequence` 초과 시 `RAISE EXCEPTION`(함수 전체의 `EXCEPTION WHEN OTHERS`가 잡아 자동 롤백 — 별도 카운터 되돌리기 로직 불필요, Stage에서 실제로 카운터 롤백 확인).
- **1단 계층에도 issue_seq 부여**(Stephen 확정) — 상품의 "1단=순번 없음" 정책과 의도적으로 다르게 적용. 쿠폰은 "코드" 컬럼이 관리자의 1차 식별자이기 때문.
- **`generate_user_coupon_redeemed_code`(고객 사용 시점 실채번) 무변경** — issue_seq는 CMS 표시 전용이고, 고객에게 실제 발급되는 코드(사용 시점 채번)는 이번 수정과 완전히 별개 숫자다. "발행 개수 식별"과 "사용 코드 상한"을 한 숫자에 섞지 않기 위한 의도적 분리(Stephen 확정).
- **목록 표시(`coupon/+page.svelte codeDisplay()`)**: `code_series.issue_seq`가 있으면 0-패딩 대신 이 실값으로 표시. 2단 계층(`parent_max_sequence` 존재)이면 발행순번 구간만 issue_seq로 채우고 자식 순번 구간은 그대로 0 유지(products.md QR-LABEL-2와 동일 원칙). issue_seq가 없는 구버전 발급분은 기존 0-패딩 그대로 하위호환.

### ⚠️ Stage 적용 중 발견한 함정 — 오버로드 중복 (products.md의 PGRST203 사례와 동일 클래스)
`cms_create_coupon`에 트레일링 파라미터(`p_auto_distribute_enabled`)를 추가할 때 처음에는 기존 함수처럼 DROP 없이 `CREATE OR REPLACE`만 실행했는데, **Postgres는 파라미터 개수가 다르면 "교체"가 아니라 새 오버로드로 추가한다** — Stage에 30-param/31-param 두 함수가 동시에 남는 것을 실제로 확인(`pg_proc` 조회). PostgREST가 named-parameter 호출 시 어느 쪽에 매칭할지 모호해지는 위험(products.md `generate_product_code` 2/3-param 오버로드 사고와 동일 클래스). **30-param 오버로드를 명시적으로 DROP한 뒤에야 1개만 남는 것을 확인**했고, 마이그레이션 파일(`556_*.sql`)에도 이 DROP을 반영해 재실행 시 동일하게 안전하도록 정정했다.

### Stage 검증 (SQL 직접 실행, `BEGIN...ROLLBACK`으로 잔존 데이터 없이 확인)
- 같은 코드조합으로 2회 연속 생성 → `code_series.issue_seq`가 1, 2로 정확히 증가.
- `parent_max_sequence=1`인 조합에 2회 생성 시도 → 2번째 호출이 `COUPON_ISSUE_SEQ_EXCEEDED`로 정확히 거부(에러 메시지에 "현재=2" 포함 — 카운터가 실제로 2까지 증가했다가 예외로 되돌아가는 것을 별도 트랜잭션에서 확인).
- `discount_type='percentage'`, `discount_value=150` 생성 시도 → `coupons_percentage_discount_max_check` CHECK 위반으로 `ok:false` 반환(원문 에러 메시지 그대로, 서버단 선제 차단과 별개의 최종 방어선).
- 위 3건 전부 `ROLLBACK`으로 정리 — Stage에 테스트 데이터 잔존 없음.

### 변경 파일

- 신규: `supabase/migrations/20260927050000_556_cms_create_coupon_issue_seq_auto_distribute.sql`(DROP 30-param + CREATE 31-param, issue_seq 로직 + `p_auto_distribute_enabled` 포함)

## 2. 3 — "자동 발행" → "자동배포" 토글 통일

### 배경
생성 화면의 "자동 발행 활성화" 토글(`auto_issue_enabled`/`auto_issue_schedule`)과 발행관리 상세 패널(`CouponDetailPanel`)의 "자동배포 활성/중지" 토글(`auto_distribute_enabled`, Migration #527)이 서로 다른 컬럼을 다루는데, `cms_create_coupon` INSERT문이 `auto_distribute_enabled`를 지정하지 않아 **생성 화면의 토글 상태와 무관하게 모든 신규 쿠폰이 항상 "자동배포 활성"으로 시작**하는 결정적 결함이었다.

### 조치
- `new/+page.svelte`: "자동 발행"(매월/기간 스케줄 + 배포대상 라디오) 섹션 전체 제거 → `CouponDetailPanel`과 동일한 단일 "자동배포" 토글로 교체(기본값 `true`, DB 기본값과 동일 유지). 상태값·derived(`autoScheduleJson`/`distTargetJson`)·연관 CSS(`.auto-box`) 함께 삭제.
- `new/+page.server.ts`: `auto_issue_enabled`/`auto_issue_schedule`/`distribution_target` 파싱·검증 로직 제거, `p_auto_distribute_enabled` 파라미터 추가.
- `cms_create_coupon`(Migration #556): `p_auto_distribute_enabled boolean DEFAULT true` 파라미터 추가 + INSERT 컬럼에 반영(§1의 issue_seq 수정과 같은 마이그레이션에 합산).
- `auto_issue_enabled`/`auto_issue_schedule`/`distribution_target` 컬럼 자체는 삭제하지 않음(요청 범위 밖, 다른 참조 가능성 미확인) — 생성 화면이 더 이상 이 값을 채우지 않을 뿐.
